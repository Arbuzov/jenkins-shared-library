# runFirmwarePipeline

Declarative pipeline for an *SBC firmware* repository: builds the ISO and the firmware image,
publishes them to Nexus, deploys and tests them, tags the release and writes the release notes.

Everything that differs between firmware repositories lives in a per-branch config file
(`jenkins.yml` by default), so each repository keeps a two-line `Jenkinsfile`.

The config is read with `readTrusted`, which resolves from SCM *before a workspace exists* —
that is what lets its values drive the build parameters. It therefore only works in
**multibranch** jobs.

## Usage

```groovy
@Library('asatnet@master')_
runFirmwarePipeline()
```

With overrides:

```groovy
runFirmwarePipeline(
  CONFIG: 'jenkins.yml',
  REPOSITORY: 'bullseye',
  AGENT_LABEL: 'farmer-docker-ubuntu'
)
```

## Parameters

All parameters are optional and passed through a Map:

| Parameter | Default | Description |
|-----------|---------|-------------|
| `CONFIG` | `jenkins.yml` | Path of the config file, resolved with `readTrusted` |
| `REPOSITORY` | `bullseye` | Debian repository the pinned components' version choices are read from, in a single index fetch |
| `BUILD_IMAGE` | `registry.nexus.asatnet.net/spacebridge/firmware-build:bullseye-b1` | Docker image the build runs in |
| `BUILD_ARGS` | `--privileged -v /srv/docker/dual-image:/home/dual-image/` | Docker arguments for that image |
| `AGENT_LABEL` | `farmer-docker-ubuntu` | Node label the pipeline runs on |
| `NEXUS_CREDENTIALS_ID` | `nexus-publisher` | Jenkins credential the deploy stages publish to Nexus with |

`nexus-publisher` has to exist in Jenkins, scoped to publishing to Nexus and nothing else.
Both deploy stages fail without it — it replaces `jira-username-password`, which carried far
more access than uploading an artifact needs.

## Build retention

`buildDiscarder` is set per branch, because the ISO and the firmware image are large and
every non-MR build is published to Nexus anyway:

| Build | Builds kept | Artifacts kept |
|-------|-------------|----------------|
| Merge request | 3 | 3 |
| Any other branch | 30 | 10 |

Artifacts are kept for fewer builds than the builds themselves: the ISO and the firmware
image dominate the disk, and the iso/fw/syft set of every non-MR build also lives in Nexus
under `maven-releases`.

## Config file

```yaml
project: estella-hd                          # artifactId and Manifest/tag naming
jiraProject: EH                              # Jira project the version is created in
mavenGroup: com.spacebridge.sbc-firmware     # Nexus groupId
releaseNotesSpace: PSIN                      # Confluence space for the release notes
releaseNotesRoot: '575111187'                # parent page id - quote it, or YAML makes it an int
installationSpace: PSIN
installationRoot: Host eStella-HD system installation
testSbcIp: 192.168.65.188                    # optional, used by the test stages
keyComponents:
  dataplane-phs-ng:
    project: ASAT3-PHS/asat3%2Fphs%2Fdataplane-phs-ng/release_1.0.x   # Jenkins job path
    buildMask: '(?<=b)\d+'                   # single quotes, so YAML keeps the backslash
    pinned: true
```

`keyComponents` is the single registry of the components the release notes report on:

- `pinned: true` — we choose the version. The component gets a `<NAME>_VERSION` build parameter
  (key uppercased, `-` to `_`) and is written to `Manifest`, so the key must be both the debian
  package name and the `Manifest` key.
- `pinned: false` (or absent) — we only track it. It appears in the changelog with whatever
  version `syft` found in the built image, and gets no build parameter.

Order in `keyComponents` is the order of the parameters in the build UI. When nothing is
pinned, the *Software Versions* section is omitted entirely.

## Build parameters

`<NAME>_VERSION` per pinned component (empty = keep the `Manifest` version), plus:

| Parameter | Description |
|-----------|-------------|
| `FIRMWARE_VERSION` | New value for the `VERSION` file (empty = keep current) |
| `CREATE_GIT_TAG` | Tag the deployed commit as `v<version>`, after a successful production deploy |

## Returns

No return value (defines and runs a Jenkins declarative pipeline).

## Failure behavior

- The config is validated before any parameter is rendered: an empty or unparsable file, a
  missing key, an empty `keyComponents`, or an entry without `project`/`buildMask` fails the
  build with `error(...)` naming everything that is wrong at once.
- Running the job manually with `FIRMWARE_VERSION` or a `<NAME>_VERSION` set commits the change
  through `gitlabUpdateFile` and stops the build — the GitLab webhook starts the real one. If
  the requested versions are already in `Manifest` and `VERSION`, nothing is pushed and the
  build fails rather than reporting a handoff that will never arrive.
