# runFirmwareConfigurator

Declarative pipeline that selects Debian package versions and a firmware release version, then updates an existing firmware repository.
Configurator repositories keep only:

```groovy
@Library('asatnet@master')_

runFirmwareConfigurator()
```

## Configuration

`CONFIG` defaults to `jenkins.yml`, read with `readTrusted` before allocating an agent. Requires a multibranch job.

```yaml
firmwareRepo: https://gitlab.asatnet.net/asat3/estella-hd/estella-hd-firmware
repository: bullseye
```

`firmwareRepo` is required (HTTP(S), without embedded credentials). `repository` defaults to `bullseye`.
Without an explicit `branch`, normal builds target `env.BRANCH_NAME`. MR builds always preview `env.CHANGE_TARGET`,
never `MR-<n>` or the MR source branch; a missing target fails instead of guessing master.
An explicit `branch` remains supported for compatibility, but writes require it to equal the job's branch.
Other keys are rejected. Manifest uses plain, unique `package=version` entries; blank lines and standalone comments are supported.

## Parameters and execution

Every Manifest package gets `<PACKAGE>_VERSION`, with punctuation replaced by underscores, versions from
`getRepReproArtifacts` in one index fetch, sorted by `sortDebianVersions`.
Colliding parameter names fail. `... (current)` keeps the value read at build time; `FIRMWARE_VERSION` is an optional `X.Y.Z` string.
The actual Manifest is authoritative, rather than the firmware release-notes component registry.

The stages refresh parameters, validate the selected inputs, update firmware and link its current build.
Each matching branch refreshes every five minutes. Automatic builds do not write. A user-started branch build outside an MR
with changes calls `gitlabCommitFiles` once for all changed files, targeting only its same-named firmware branch.
MRs and builds with an explicit mismatched target preview changes only and do not install a refresh timer.
The write method also checks the user cause and branch/MR guard before making an API call.
Configurator branches are created manually; there is no synchronization or branch-creation step.
A missing firmware counterpart fails the read without falling back to another branch or creating one.

VERSION is read at the Manifest's commit, so both belong to the same snapshot. Manifest edits use
`applyManifestVersions` and are parsed back to exactly the expected package map. File updates include their
`last_commit_id`, preventing a stale update from overwriting a concurrent edit. No retry drops that guard.
GitLab's commit webhook starts the normal firmware build; no explicit Jenkins build duplicates it.

The commit names the versions and requester and includes the existing `Jenkins-Upstream-Project` and
`Jenkins-Upstream-Build` trailers. If there are no changes, GitLab commit statuses link the current numbered
Jenkins build via `linkUpstreamBuild(reverse: true)`. No numbered status means no link and no new build.

The pipeline keeps ten builds, disables concurrent runs and stage restart. Git tag creation remains in
the firmware pipeline and is not carried in the commit. No return value.

## Errors

Invalid config, malformed/duplicate Manifest entries, parameter-name collisions, index failures,
unavailable selected versions, invalid firmware versions, incorrect Manifest edits and GitLab commit
conflicts fail before a successful write. Existing API/build-link helpers provide GitLab access and linking.
